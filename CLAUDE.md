# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

**Deployment**: GitHub Actions → GitHub Pages (kevintraywick.com). The `deploy.yml` workflow builds on push to `main` and injects `VITE_API_URL` and `VITE_POST_SECRET` from GitHub secrets.

**Backend**: External API at `https://kt-feed-api-production.up.railway.app` — Railway service **"kev's web site"** in project `inspiring-optimism` (don't trust `~/kt-feed-api`'s link; it once pointed at the empty `airy-flexibility` project). Source is the separate repo `~/kt-feed-api` (GitHub auto-deploy). Configured via `VITE_API_URL` env var. The `useFeed` hook handles all API calls. `POST /entries`, `PATCH /entries/:id` (pan position), and `DELETE /entries/:id` (also deletes its comments) need the `VITE_POST_SECRET` Bearer token; `POST /uploads` needs no auth (images, 10MB cap); `GET /entries` returns only the 20 newest of everything; `GET /entries?kind=photo|note` returns up to 100 of one kind (anything else is a 400), which is what the homepage's two boxes use. Note the "secret" ships in the public JS bundle — any visitor could technically post or re-pan; accepted for a personal site. CORS allows only kevintraywick.com and localhost 5173/4173 — a Vite dev server that falls back to another port (e.g. 5174) silently can't reach the API. If every request 502s while Railway shows the service "Online", the app has hung: `cd ~/kt-feed-api && railway redeploy -y`. `GET /proxy?url=` (`src/proxy.js`) re-serves a remote HTML page from this origin so the flipbooks can iframe sites that refuse framing; it's an open proxy, so the guards matter — http(s) only, DNS checked against private/loopback/link-local/CGNAT/metadata ranges **on every redirect hop** (not just the first), 5MB cap, 12s timeout, HTML content-types only, per-IP rate limit, upstream cookie/framing headers never copied through. Only the top-level document is proxied: an injected `<base>` sends the page's CSS/images back to the origin, which is fine because subresources aren't subject to framing rules. Tests: `cd ~/kt-feed-api && npx jest --runInBand`.

**Routing** (in `App.tsx`):
- `/` → Homepage (redesigned 2026-11-12): three panes, each one cell of the old 3×3 grid, across the middle row — `PhotoPanel` (left), `NameFlip` (center), `ThoughtPanel` (right). Under `md` they stack full-width. The old nine-panel link grid is gone; the sub-apps still live at their own URLs but nothing on the homepage links to them.
- `/blog` → Blog feed (all entries)
- `/blog/:id` → Individual entry with comments

**Homepage panes** (`src/components/`): `NameFlip` is the name in Instrument Serif (Google Fonts link in `index.html`, `.name-flip*` rules in `index.css`); a mouse over it turns it to the phone number, and on touch the first tap flips and the second follows the `tel:` link — the click handler `preventDefault`s only while unflipped. `PhotoPanel` is `grayscale` until the pane is hovered (`group-hover:grayscale-0`); arrows, drop-upload and drag-to-pan are unchanged. `ThoughtPanel` shows one post at a time with its date and time, its replies threaded under it, and the same older/newer arrows. **Clicking the box opens a write line** (there is no always-visible input and no `?write` switch any more): on an existing post, Enter adds a reply — a comment on that entry via `POST /entries/:id/comments`, which is unauthenticated, so any visitor can reply; on the blank page opened by the always-visible **+** circle on the box's right border (same circle as the arrows; it drops just beneath the newer arrow when that has the centre spot) (`index === -1`; it was first a hover-only `+` arrow at the newest post, which Kevin never found), Enter creates a new post (`title` = first six words, `note` = the text). Enter commits and closes the write line — nothing is editable afterwards; Shift+Enter is a line break; an empty line closes on blur. A post's thread is fetched (`GET /entries/:id`) the first time it is shown, only if `comment_count > 0`. Each pane calls `useFeed('photo')` / `useFeed('note')` → `GET /entries?kind=` (up to 100 of that kind; a note is an entry with `note` and no `image_url` or `link`), and also filters client-side so it still works against an API that ignores `kind`. Entry `created_at` is zone-less SQLite UTC — `formatDateTime` reads it as UTC; the older `formatDate` doesn't.

`index.html` includes a GitHub Pages SPA redirect shim: query param `?path=` is rewritten to the real path via `window.history.replaceState`.

**Data flow**: `useFeed` (custom hook) → fetches entries/comments, exposes `postEntry`/`postComment` → consumed by `PhotoPanel`, `Blog`, `BlogEntry`. `PhotoPanel` shows entries that have `image_url`; an image drop downscales client-side to 2400px JPEG (10MB API cap), uploads via `POST /uploads`, then posts an entry with the date as title. Dragging straight from the macOS Photos app works (Photos exports a JPEG mid-drag) — that's the intended one-step "share to site" path; a Photos share-sheet entry would need a Shortcut or an Xcode share extension, deliberately skipped. The photo renders with `object-cover` (center-crop by default); pointer-dragging the image pans it by adjusting `object-position`, and on release the position saves to the entry (`pan_x`/`pan_y`, 0–100 percentages) via `updateEntryPan` → `PATCH /entries/:id`, so all visitors see the same framing. Pan drag distance maps 1:1 to the image's cover overflow (computed from `naturalWidth/Height` vs the rendered rect); `draggable={false}` keeps it from fighting the file-drop zone.

**Public sub-apps** (`public/fast-french/`, `public/justedit/`, `public/me/`, etc.): served as-is on GitHub Pages — Vite only processes `src/`, so these files never see `import.meta.env`/`VITE_*` vars. A static page needing a build-time secret embeds a `__PLACEHOLDER__` token that `deploy.yml` string-replaces with the real value in a post-build step (see the Just Edit step) — same "ships in the public bundle" trust model as `VITE_POST_SECRET` in the React bundle, just applied by hand since no bundler touches these files.

**Just Edit** (`public/justedit/justedit.html`, no longer linked from the homepage): a plain textarea autosaved to `localStorage` only — no network calls for the text itself, so neither Kevin nor visitors can see what the other typed. Its "Drop" button POSTs `{title, body}` to kt-feed-api's `POST /me-notes` (title = first ~6 words, Bearer-authed like `/entries`) so the note shows up on `/me`.

**`/me`** (`public/me/index.html`, no longer linked from the homepage): a flipbook like `/cc` but simpler — no `deletedServerNames` tracking, so deleting a `files.json`- or API-sourced item only hides it until the next reload (not a real delete). Sources merge three ways on load: static `files.json`, this browser's `localStorage['me_flipbook']` (manual drops), and kt-feed-api's `GET /me-notes` (dropped notes — fetched fresh every load, never cached to localStorage, which is what makes them sync across devices instead of staying on one browser).

**CC Flipbook** (`public/cc/`): A standalone flipbook viewer for cheat sheets. Pages defined in `files.json` (images, PDFs, local HTML) plus user-added files/URLs persisted in IndexedDB (migrated from legacy localStorage; localStorage's ~5MB quota dropped large screenshots). User deletions of `files.json` pages are tracked in a `deletedServerNames` list so the server-file merge doesn't resurrect them on reload. Supports drag-to-reorder thumbnails, URL webpage embedding (type `"url"`), and file drop/upload. HTML data URLs use `srcdoc` (not `src`) to avoid browser download behavior. **`public/collect/` is a near-identical clone** (adds `?box=<slug>` storage keys + API image upload, drops IndexedDB/`deletedServerNames`) — a fix to one nearly always belongs in both, same as `basher/` vs `public/basher/`. Drops are handled **page-wide** (`handleDrop` on `document`), not on the 48px `+` circle: `text/uri-list` is RFC 2483, so parse it line-by-line and skip `#` comment lines, and never gate URL handling on `dataTransfer.files.length` — macOS attaches a `.webloc` when you drag a link out of Finder/Mail/Notes, and `.webloc`/`.url` shortcuts are read as text to pull the link out. `type: "url"` pages render through kt-feed-api's `/proxy` (framing them directly leaves a blank pane), sandboxed **without** `allow-same-origin` since the proxied HTML is served from the API's own origin.

**Basher** (`public/basher/`, served at `/basher`): Static frontend for the business-plan evaluator. The drop zone uploads to **`basher-api/`** (separate Railway service in this repo) which extracts text, calls Claude, renders 5 HTML report pages, and stores them on a Railway volume at `/app/data/{slug}/` for **10 days**. After upload the user is redirected to the report URL and a download button (zip) is shown in a banner on every report page. `basher/` is a parallel dev workspace that mirrors `public/basher/` — keep them in sync (rsync on changes), or treat `public/basher/` as source of truth.

**Dark Skies** (`darkskies/`, live at `darkskies.kevintraywick.com`): a **standalone** Node + Express + Postgres app with its own Railway service — NOT part of the Vite build. Notes: `darkskies/CLAUDE.md`.

**Monster Spray** (`monster/`, for `monster.kevintraywick.com`): a **standalone** Express app with its own Railway service — NOT part of the Vite build. Notes: `monster/CLAUDE.md`.

**NYC 2026** (`nyc2026/`, live at `nyc2026.kevintraywick.com`, plus `/wendy` and `/demo`): a **standalone** Express app with its own Railway service — NOT part of the Vite build. Every change is judged on "would they get it without being told". Notes: `nyc2026/CLAUDE.md`.

**160 Weldon** (`weldon/` + `weldon-api/`, live at `160weldon.kevintraywick.com`): house-info site + API, a **standalone** Railway service — NOT part of the Vite build. Site source of truth is `weldon/site/`; sync before committing: `rsync -a --delete weldon/site/ weldon-api/site/`. Never exercise a prod insert route to test. Notes and gotchas: `weldon-api/CLAUDE.md`.

## Design direction & Jelly UI

**Affordance rules across all the sub-apps**: styling is a promise about behavior — if two controls look the same they must act the same. `/cc`'s 🔗 button and `+` drop zone shared one CSS rule (identical 48px dashed circles) but only `+` accepted drops, and the whole feature read as dead. Related: never let an interaction fail silently. A document-level `preventDefault()` was swallowing every drop that missed the target, so a working feature and a broken one looked identical — unhandled input should say something (a toast here). And prefer a generous target: the page-wide drop zone replaced a 48px circle you had to hit exactly.

**A card-sized copy of a full-page widget is not the same component.** The Location map was 520px with wheel zoom on; on the Dashboard it's `#map-mini` at 260px (matching the chart cards, so it comes out level with the card beside it) with **`scrollWheelZoom: false`** — an embedded map that swallows the scroll wheel mid-page is a well-known annoyance, and the +/− control and double-click still zoom. Check too what the full page carried *around* the widget: Location's prose credited OSM/Esri, and that survived deletion only because both `tileLayer`s pass `attribution` and Leaflet's own control renders it.

**Two controls that share a look need to be separable in code, not just to the eye.** The To do page's priority picker reuses `.statusselect` for its pill shape, which means the status handler's `closest('select.statusselect')` matched it too; the handler now reads `select.statusselect:not(.prioselect)`. Related: when a control's value can be "none", make that a **real option** ("Not set") rather than a blank placeholder — and store it as an explicit empty rather than deleting the row, or an override meaning "cleared" is indistinguishable from no override at all.

**Escape any user-authored text before it goes into `innerHTML`.** These pages build rows by string concatenation, and anything that arrived through an API (hand-added task text, a scanned vendor name) is user input: the Dashboard's urgent pane and the Records/Estimates rows all run their fields through a local `esc()`.

Kevin is exploring a **native iOS app** (SwiftUI, not part of this repo/Vite build) whose design language is based on **Jelly UI** (https://jelly-ui.com), chosen for its restraint + playfulness. Frame a design system as two layers: **design language** (aesthetic + tokens + motion feel — portable across platforms, the reusable core: Jelly's soft/tactile look, "soft-body physics" spring motion, dark mode + RTL, WCAG AA tokens) vs **implementation** (platform-specific, NOT portable — Jelly is a Web Components library, so a *web page* drops it in as-is but *native iOS* rebuilds the aesthetic from scratch in SwiftUI). A rendering framework (React, Web Components, SwiftUI) is the *medium* the design is expressed in, not part of the design system itself.

**Design Language Builder** (`public/design/`, live at `/design`) is built with Jelly UI; its notes and the Jelly UI gotchas are in `public/design/CLAUDE.md`.

## Gotchas

- `.gitignore` ignores `*.svg` repo-wide — `git add -f` any SVG that must be committed (e.g. favicons).
- ESLint runs the strict React-compiler-era hooks rules: no ref reads during render (`react-hooks/refs` — e.g. use Tailwind `active:` for a drag cursor instead of `ref.current ? … : …` in JSX) and no plain `setState` in a `useEffect` body (`react-hooks/set-state-in-effect` — to reset state when a prop/id changes, use the documented adjust-state-during-render pattern: keep the previous id in state and call both setters inside an `if (id !== prevId)` during render).
- Bare `npx vitest run` / `npm run lint` also sweep stale checkout copies under `.claude/worktrees/**` and `basher/.claude/worktrees/**` — scope to your files (`npx vitest run src`, `npx eslint <files>`) to judge a change; repo-wide lint carries ~80 pre-existing problems.
- Multiple Claude sessions often share this checkout and its git index — commit with explicit pathspecs and check `git diff --cached --stat` first; a blanket commit once swept another session's staged deletions to main and broke the Pages build.
- `railway logs` shows the **current deployment only** — a push/redeploy restarts the container and wipes prior output. weldon-api logs errors only, so debug by reproducing the request, not by log archaeology.
- Anthropic structured outputs: enums may not mix strings with null — use an `'unsure'` sentinel and map to NULL server-side; nullable scalars (`type: ['number','null']`) are fine.
- Multiple Claude sessions may work in this repo at once — `git commit` sweeps in ANY staged changes, including another session's. Check `git status` for foreign staged work first, or commit with explicit pathspecs (`git commit -m … -- <paths>`).
- Safari ignores express.static's default `public, max-age=0` and serves stale HTML for days. weldon-api sets `Cache-Control: no-cache` on HTML (assets: `max-age=0, must-revalidate`) — keep those headers.
- Railway's GraphQL API (`https://backboard.railway.com/graphql/v2`, token = `user.accessToken` in `~/.railway/config.json`) is fully introspectable — query `__schema` to discover mutations/args. Volume backup mutations exist but return "Not Authorized" on the Hobby plan (Pro-gated).
- The first requests right after a Railway deploy goes live can 502 intermittently for a minute or two (container churn, silent — no crash trace in logs). Retry and probe `/api/health` before debugging the code; a real crash pattern is *reproducible*, churn isn't.
- **Confirming *which commit* is live on Railway**: `railway status --json` returns an empty `latestDeployment` (an until-loop on it never fires), and a `railway logs` boot line can be the **previous** deployment's — so "container started" is not proof your push is live. Ask the GraphQL API instead: `deployments(first:4, input:{serviceId:"…"}){edges{node{id status createdAt meta}}}` returns `status` plus `meta.commitHash`/`commitMessage`, so you can match the SHA you pushed (superseded deploys read `REMOVED`). `railway logs --build` is the other tell — its `modified file:` lines and base-image pulls belong to whichever build is current.
- kt-feed-api local test pattern: `DB_PATH=':memory:' POST_SECRET=<x> PORT=<x> node src/server.js` for a disposable instance — same idea as weldon-api's scratch `DATA_DIR`.
- Most sites refuse to be iframed (`X-Frame-Options`, CSP `frame-ancestors`) — claude.com and google.com send SAMEORIGIN, github.com and nytimes.com send DENY. The pane just renders blank with no console error worth finding. Check with `curl -sSI -L <url> | grep -iE 'x-frame-options|content-security-policy'` before assuming the embed code is broken; the only fix is proxying through our own origin.
- `iframe.sandbox = '…'` (property assignment) does not reliably set the attribute — it reflects a `DOMTokenList`, and where the assignment doesn't forward, the attribute is omitted entirely, which means **no sandbox at all** rather than a strict one. Always `setAttribute('sandbox', …)`. Same trap shape as any `[PutForwards]` DOM property.
- Testing a static `public/` page's client-side JS in jsdom (no browser extension connected) needs two polyfills jsdom lacks — `window.fetch = fetch` and `window.Element.prototype.scrollIntoView = () => {}` — set via the `beforeParse` option, not after `new JSDOM()` (inline `<script>`s already ran by then). Also: top-level `let`/`const` in an inline script don't attach to `window` (unlike `var`) — inspect the rendered DOM, not `window.<name>`. Run such scripts **from the repo root** so `node_modules/jsdom` resolves — a copy in the scratchpad dir won't.
- Simulating drag-and-drop in jsdom: there is no `DragEvent`/`DataTransfer`, so dispatch a plain `new window.Event('drop', {bubbles:true, cancelable:true})` and hang your own `dataTransfer` on it (`{files, getData, types}`) — enough to exercise real drop handlers. But jsdom can't decode images, so `/cc`'s `compressImage()` never resolves (`img.onload`/`onerror` never fire) and an image drop adds no tile; diff against the pre-change file (`git show <sha>:<path>`) before calling that a regression.
- kt-feed-api's image uploads write to `UPLOADS_DIR` (code default `/app/data/uploads`, matching the volume mount). A stale `UPLOADS_DIR=/data/uploads` env var — leftover from before the volume was moved to `/app/data` — silently overrode that default: uploads served fine right up until the next redeploy wiped ephemeral storage and 404'd every photo, even though the DB entries survived. If photos vanish after a deploy but entries don't, check `railway variables --json` for that var before anything else. Deploying a fix: setting an env var (`railway variables --set`) or pushing to `main` both trigger an auto-redeploy on their own — `railway redeploy -y` then fails with "cannot be redeployed... currently building/deploying"; just poll `railway status` instead of retrying it.
